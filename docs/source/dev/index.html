6. 개발자 문서

OpenFAST 개발자로서 우리의 목표는 잘 테스트되고 문서화되었으며 자립 가능한 소프트웨어를 보장하는 것입니다. 이를 위해 우리는 기능 추가 및 개선과 함께 문서화 및 테스트 범위를 개선하기 위해 지속적으로 노력하고 있습니다. 문서의 이 섹션에서는 외부 개발자가 코드 개발 시 NLR OpenFAST 팀과 협력할 수 있도록 확립한 프로세스 및 절차를 간략하게 설명합니다.

일반적인 OpenFAST 개발에 도움을 주거나 특정 기능에 대한 작업을 하고 싶다면 먼저 다음 지침에 따라 OpenFAST를 설치하세요. 설치 지침 당신의 기계를 위해. 다음으로, 다음 테스트 스위트를 실행하여 설치가 유효한지 확인하십시오. 테스트 지침. OpenFAST가 컴파일되는 동안 다음 내용을 읽어 보시기 바랍니다. 개발 철학 및 지침 섹션에서는 개별 개발 및 공동 개발을 위한 일반적인 작업 흐름을 이해합니다. 마지막으로 반드시 검토해 보세요. GitHub 작업 흐름 병합 또는 코드 충돌을 방지합니다.

NLR, 업계 파트너 및 대학 간에 개발이 병행되면서 NLR는 GitHub를 사용하여 다음과 같은 노력을 조정합니다.

  • GitHub 문제 사용법이나 개발에 관한 질문을 하고, 버그를 보고하고, 코드 개선 사항을 제안하는 곳입니다.

  • GitHub 풀 요청 OpenFAST 팀과 협력하여 새 코드를 기본 저장소에 병합할 수 있는 곳입니다.

OpenFAST에 관한 기타 질문이 있는 경우 다음으로 문의하십시오. 마이크 스프래그.

6.1. 개발 철학 및 지침

OpenFAST는 자립형 커뮤니티 개발 소프트웨어로 만들어졌습니다. NLR OpenFAST 팀이 저장소의 문지기 역할을 하는 동안 우리는 커뮤니티가 새로운 아이디어를 공유하고 코드를 기여하도록 적극적으로 장려합니다. 코드 기여에 대한 고려 사항은 여기에 설명되어 있습니다.

6.1.1. NLR와의 참여

커뮤니티 코드 기여 프로세스는 NLR OpenFAST 팀과 직접 협력하여 작업 범위를 정의하고 개발 노력을 조정하는 것부터 시작됩니다. 많은 그룹이 OpenFAST를 동시에 작업하기 때문에 이는 특히 중요합니다. 조기에 참여함으로써 모든 개발자는 최신 상태를 유지하고 코드 병합 중에 충돌을 최소화할 수 있습니다. 선호되는 의사소통 방법은 GitHub 문제. 초기 게시물에는 계획된 개발 작업, 영향을 받을 소프트웨어 영역 및 모델 검증 자료에 대한 모든 관련 정보가 포함되어야 합니다. 보다 개발 계획/실행 계획 계획된 작업 설명에 대한 자세한 내용은

NLR OpenFAST 팀은 항상 우리의 관심이 가장 많이 필요한 내부 프로젝트를 진행하고 있지만 합리적인 시간 내에 커뮤니티에 참여하고 개발 노력을 지원하기 위해 모든 노력을 기울일 것입니다. 문제를 게시한 후 NLR OpenFAST 팀에서 연락하여 세부 사항을 논의하기 위한 회의 일정을 잡을 수 있습니다.

6.1.2. 개발 계획/실행 계획

NLR의 중요한 코드 개발 노력은 상세한 구현 계획 개발로 시작되며, 이러한 계획 중 일부를 다운로드하여 참조할 수 있습니다.

  • Development Plan for the Aerodynamic Linearization of OpenFAST

  • FAST.Farm Development Plan.

  • Implementation Plan - 2nd-order Forces Within HydroDyn

  • Implementation Plan - 2nd-order Wave Kinematics Within HydroDyn

OpenFAST의 모듈화 프레임워크 내의 좋은 계획은 다음에서 사용하는 정의와 명명법을 따릅니다. NWTC Programmer's Handbook. 다음 정보를 전달해야 합니다.

  • 모듈이 느슨한 결합, 타임 행진을 위한 긴밀한 결합 및/또는 선형화용인지 여부를 명시합니다.

  • 모듈의 입력(초기화 포함), 출력(초기화 포함), 상태(연속, 이산 및 제약 조건) 및 단위를 포함한 매개변수를 정의합니다.

  • 모듈에 대한 예제 입력 파일을 배치합니다.

  • 야코비 행렬(강한 결합 및 선형화용)을 포함한 모듈의 수학적 공식을 프레임워크에 필요한 형식으로 설명합니다.

  • 모듈의 입력이 다른 특정 모듈의 출력에서 ​​파생되는 방법을 규정합니다.

  • 잠재적인 수치 문제와 코드에서 이를 방지하는 방법을 식별합니다.

  • 어떤 수학 공식이 어떤 서브루틴에 사용되는지 식별하고 솔루션 프로세스에 사용되는 알고리즘을 설명하는 것을 포함하여 의사 코드(실제 코드와 반대)를 사용하여 모듈의 서브루틴을 배치합니다.

이 정보는 소스 코드를 변경하기 전에 계획을 검토하고, 반복하고, 동의하는 것이 더 쉽기 때문에 매우 유용합니다. 또한 구현 계획은 프로그래밍 노력에 큰 도움이 되며 사용자 작성 및 문서 개발을 위한 유용한 시작점이 됩니다.

6.1.3. 좋은 제출의 조건

개발 노력에는 개발 프로세스 전반에 걸쳐 적절한 테스트가 포함되어야 합니다. 가능하다면 새로운 서브루틴에는 단위 수준 테스트가 포함되어야 하며 기존 회귀 테스트는 주기적으로 실행되어 전체 시스템 동작이 의도치 않게 변경되지 않았는지 확인해야 합니다. 새로운 기능의 경우 새 코드를 다루기 위해 추가 회귀 테스트를 추가해야 합니다. 회귀 테스트 결과가 예상대로 변경되면 기준 결과를 로컬에서 업데이트해야 합니다. openfast/r-테스트 저장소. 그만큼 r-테스트 README 기준선 업데이트에 대해 설명하고 OpenFAST 테스트 이 문서의 섹션에는 테스트에 대한 추가 세부 정보가 포함되어 있습니다.

새로운 코드는 개발자와 사용자 관점 모두에서 견고성을 고려해야 합니다. 다음은 코드 개발 중에 고려해야 할 몇 가지 질문입니다.

  • 다른 개발자가 서브루틴을 사용하는 방법을 명확하게 알 수 있습니까?

  • 새 코드가 명확하고 예측 가능한 동작을 나타냅니까?

  • 다양한 품질의 데이터에서 코드는 어떻게 작동합니까?

  • 코드가 시뮬레이션 성능에 어떤 영향을 미치나요?

또한 사용자 및 개발자 문서가 새 코드에 포함되어야 합니다. 사용자 문서에는 이론, 모델링 지침, 입력 및 출력에 대한 설명이 포함됩니다. 사용자 문서는 다음에 설명된 온라인 문서의 일부로 포함되어야 합니다. 문서 개발. 개발자 문서는 일반적으로 소스 코드의 주석에 포함됩니다. 여기에는 서브루틴 API(입력 및 출력)뿐만 아니라 명확하지 않은 알고리즘이나 코드 줄도 설명되어야 합니다. 2년 동안 코드를 다시 볼 수 없다면 코드를 완전히 이해하기 위해 알아야 할 것이 무엇인지 스스로에게 물어보세요.

6.1.4. 검토 및 NLR 피드백을 위해 제출

NLR OpenFAST 팀의 검토를 위해 새 코드를 제출할 수 있습니다. 풀 리퀘스트 에 설명된 대로 GitHub에서 OpenFAST 작업. 우리는 코드의 정확성, 유효성, 품질 및 견고성을 검토할 것입니다. 오픈 소스 코드 기여를 검토하는 것은 어려울 수 있으므로 자신의 코드를 검토하고 병합 준비가 되었는지 결정하는 데 도움이 되는 정보가 무엇인지 고려하는 것이 좋습니다.

검토 프로세스는 단순히 자동화된 테스트가 통과되었는지 확인하는 것부터 시작됩니다. GitHub 작업. 검토를 요청하기 전에 모든 자동화된 테스트를 통과했는지 확인하세요. 그 후 프로세스에는 리뷰어와 제출자 간의 일부 의사소통이 포함되며, 배경이나 검증에 대한 추가 정보를 요청할 수도 있고, 특정 코드 줄에 대한 추가 통찰력을 얻기 위해 끌어오기 요청에 댓글을 달 수도 있습니다.

제출자와 검토자 사이에 합의가 이루어진 후 풀 요청은 대상 브랜치(일반적으로)에 병합됩니다. 개발자) 풀 요청이 종료됩니다. 끝났어요! 이 변경 사항은 OpenFAST의 후속 릴리스에 포함될 예정입니다. 개발자 지점이 다음으로 병합되었습니다. 기본.
