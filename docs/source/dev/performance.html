6.1.6.6. 성능 프로파일링 및 튜닝

OpenFAST 팀의 주요 초점은 계산 비용이 가장 많이 드는 사용 사례에 대한 솔루션 출시 시간 성능을 향상시키는 것을 목표로 OpenFAST 소프트웨어의 성능 프로파일링 및 최적화입니다. 이 프로세스에는 일반적으로 초기 프로파일링 및 핫스팟 분석이 포함되며, 물리 모듈 및 글루 코드에서 최적화 대상으로 지정할 특정 서브루틴을 식별합니다.

이 작업의 일부는 인텔®의 NLR 지정을 통해 지원되었습니다. 인텔® 병렬 컴퓨팅 센터(IPCC).

여기에는 절차, 조사 결과 및 권장 프로그래밍 방법이 나와 있습니다. 이는 작업 문서이며 추가 연구가 완료되면 업데이트될 예정입니다.

6.1.6.6.1. 고성능 프로그래밍 기술

과학 및 엔지니어링 응용 프로그램용으로 설계된 컴파일 언어인 Fortran은 매우 효율적인 코드를 생성하는 데 매우 적합합니다. 그러나 코드를 튜닝하는 과정에서 개발자는 최고의 성능을 생성하기 위해 언어와 사용 가능한 도구(컴파일러, 성능 라이브러리 등)를 이해해야 합니다. 이 섹션에서는 포트란과 인텔® 포트란 컴파일러를 효과적으로 사용하기 위한 프로그래밍 패턴을 식별합니다. 개발자는 또한 다음과 관련된 인텔® 포트란 컴파일러 문서를 참조해야 합니다. 최적화, 일반적으로, 특히 다음 섹션에 자동 벡터화 및 공동 배열.

6.1.6.6.1.1. 최적화 보고서

복잡한 소프트웨어에서 컴파일러 최적화 성능을 평가할 때 타이밍 테스트만으로는 특정 코드 줄을 최적화하는 컴파일러의 능력을 나타내는 좋은 지표가 아닙니다. 컴파일러의 최적화 시도에 대한 하위 수준 정보를 위해 개발자는 최적화 보고서를 생성하여 벡터화, 병렬화, 메모리 및 캐시 사용량, 스레딩 등과 같은 다양한 측정항목에 대한 단계별 보고를 받아야 합니다. 개발자는 Intel® Fortran 컴파일러 문서를 참조해야 합니다. 최적화 보고서.

Linux 및 macOS의 경우 OpenFAST CMake 구성에는 사용 가능한 최적화 보고서 생성을 위한 컴파일러 플래그가 있지만 set_fast_intel_fortran_posix 매크로 openfast/cmake/OpenfastFortranOptions.cmake. 주로, qopt-report-phase 및 qopt-report 플래그를 사용해야 합니다. 최적화 보고서 옵션 보기 선적 서류 비치 추가 플래그 및 구성에 대한 자세한 내용은

컴파일러 플래그가 올바르게 구성되면 컴파일러는 확장자가 있는 파일을 출력합니다. .optrpt 다음과 같은 중간 컴파일 산출물과 함께 .o 파일. 컴파일 프로세스에서는 추가 파일이 생성되고 있음을 나타냅니다.

ifort: remark #10397: optimization reports are generated in *.optrpt files in the output location

그리고 추가 파일은 해당 위치에 있어야 합니다. CMakeFiles 각 컴파일 대상에 대한 디렉터리입니다. 예를 들어 OpenFAST의 VersionInfo 모듈에 대한 최적화 보고서는 다음 위치에 있습니다.

>> ls -l openfast/build/modules/version/CMakeFiles/versioninfolib.dir/src/
-rw-r--r--  2740 May 12 23:10 VersionInfo.f90.o
-rw-r--r--     0 May 12 23:10 VersionInfo.f90.o.provides.build
-rw-r--r--   668 May 12 23:10 VersionInfo.f90.optrpt

6.1.6.6.1.2. 오퍼레이터 힘 감소

각 수학적 연산에는 효과적인 "강도"가 있으며 일부 연산은 원본보다 성능이 더 나은 여러 감소된 강도 연산의 조합으로 동등하게 표현될 수 있습니다. 코드 최적화 단계의 일부로 컴파일러는 수학 연산의 강도를 줄일 수 있는 영역을 식별할 수 있습니다. 컴파일러는 비용이 많이 드는 모든 작업을 최적화할 수 없습니다. 예를 들어, 비용이 많이 드는 수학 연산의 일부가 파생된 데이터 유형에 포함된 변수인 경우는 자주 건너뜁니다. 따라서 비용이 많이 드는 서브루틴을 프로파일링하고 가능한 강도 감소 기회를 검색하는 것이 좋습니다.

연산자 강도 감소의 구체적인 예는 배열의 여러 요소를 상수로 나누는 것입니다.

module_type%scale_factor = 10.0

do i = 1
  if array(i) < 30.0
    array(i) = array(i) / module_type%scale_factor
  end if
end do

이 경우 실수를 곱하는 것이 실수를 나누는 것보다 비용이 적게 듭니다. 배율 인수의 역수가 루프 외부에서 계산되고 루프의 수학적 연산이 곱셈으로 변환되도록 코드를 인수분해할 수 있습니다.

module_type%scale_factor = 10.0
inverse_scale_factor = 1.0 / module_type%scale_factor

do i = 1
  if array(i) < 30.0
    array(i) = array(i) * inverse_scale_factor
  end if
end do

6.1.6.6.1.3. Coarrays

Coarrays는 단일 프로그램, 다중 데이터(SPMD) 프로그래밍 패러다임에서 배열 작업을 위한 언어 수준 병렬화를 제공하기 위해 2008 표준에서 Fortran 언어에 도입된 기능입니다. 포트란 표준은 병렬화 방법을 컴파일러에 맡기고 인텔® 포트란 컴파일러는 MPI를 사용합니다.

Coarray는 프로그램의 여러 복사본에 걸쳐 배열 작업을 분할하는 데 사용됩니다. 복사본을 "이미지"라고 합니다. 각 이미지에는 고유한 지역 변수와 공유 변수인 공동 배열의 일부가 있습니다. 공동배열은 "공동차원"이라고 하는 추가 차원을 갖는 것으로 생각할 수 있습니다. 단일 이미지(일반적으로 1번째 인덱스)가 I/O 및 문제 설정을 제어하고 이미지는 다른 이미지의 메모리에서 읽을 수 있습니다.

많은 하위 배열에서 슈퍼 배열을 구성하는 것과 같은 대규모 배열에 대한 작업(야코비 행렬 구성에서와 같이)의 경우 Fortran 08의 공동 배열 기능은 전체 계산 효율성을 향상시키는 절차를 병렬화할 수 있습니다.

6.1.6.6.1.4. 데이터 모델링 및 액세스 규칙

Fortran은 열 우선 순서로 배열을 나타냅니다. 이는 다차원 배열이 인접한 열 요소와 함께 메모리에 표시된다는 것을 의미합니다. 배열의 특정 요소가 메모리의 한 위치에 있는 경우 메모리 앞의 한 요소는 해당 열의 해당 요소 위에 있는 요소에 해당합니다.

단일 명령을 활용하려면 현대 프로세서의 다중 데이터 기능, 배열 구성 및 액세스가 열 우선 순서로 이루어져야 합니다. 즉, 루프는 가장 왼쪽 인덱스를 가장 빠르게 반복해야 합니다. 슬라이싱은 : 가능하면 가장 왼쪽 색인에도 표시됩니다.

이를 염두에 두고 데이터는 구조 배열이 아닌 배열 구조로 표현되어야 합니다. 구체적으로 이는 OpenFAST 내의 데이터 유형이 기본 배열을 포함해야 하며 배열은 일반적으로 숫자 유형만 포함해야 함을 의미합니다.

아래의 짧은 프로그램은 배열 요소와 인접 요소 사이의 메모리 거리를 바이트 단위로 표시합니다.

program memloc

implicit none

integer(kind=8), dimension(3, 3) :: r, distance_up, distance_left

! Take the element values as their "ID"
! r(row, column)
r(1,:) = (/ 1, 2, 3 /)
r(2,:) = (/ 4, 5, 6 /)
r(3,:) = (/ 7, 8, 9 /)
print *, "Reference array:"
call pretty_print_array(r)

! Compute the distance between matrix elements. Inputs to the `calculate_distance` function
! are indices for elements in the equation loc(this_element) - loc(other_element)
distance_up(1,:) = (/ calculate_distance( 1,1 , 1,1), calculate_distance( 1,2 , 1,2), calculate_distance( 1,3 , 1,3) /)
distance_up(2,:) = (/ calculate_distance( 2,1 , 1,1), calculate_distance( 2,2 , 1,2), calculate_distance( 2,3 , 1,3) /)
distance_up(3,:) = (/ calculate_distance( 3,1 , 2,1), calculate_distance( 3,2 , 2,2), calculate_distance( 3,3 , 2,3) /)
print *, "Distance in memory (bytes) for between an element and the one above it (top row zeroed):"
call pretty_print_array(distance_up)

distance_left(1,:) = (/ calculate_distance( 1,1 , 1,1), calculate_distance( 1,2 , 1,1), calculate_distance( 1,3 , 1,2) /)
distance_left(2,:) = (/ calculate_distance( 2,1 , 2,1), calculate_distance( 2,2 , 2,1), calculate_distance( 2,3 , 2,2) /)
distance_left(3,:) = (/ calculate_distance( 3,1 , 3,1), calculate_distance( 3,2 , 3,1), calculate_distance( 3,3 , 3,2) /)
print *, "Distance in memory (bytes) for between an element and the one to the its left (first column zeroed):"
call pretty_print_array(distance_left)

contains

integer(8) function calculate_distance(c1, r1, c2, r2)

    integer, intent(in) :: c1, r1, c2, r2
    calculate_distance = loc(r(c1, r1)) - loc(r(c2, r2))

end function

subroutine pretty_print_array(array)

    integer(8), dimension(3,3), intent(in) :: array
    print *, "["
    print '(I4, I4, I4)', array(1,1), array(1,2), array(1,3)
    print '(I4, I4, I4)', array(2,1), array(2,2), array(2,3)
    print '(I4, I4, I4)', array(3,1), array(3,2), array(3,3)
    print *, "]"

end subroutine

end program

6.1.6.6.2. 최적화 연구

이 섹션에서는 OpenFAST 섹션을 프로파일링하고 인텔® 컴파일러 제품군의 성능을 향상시키기 위한 구체적인 노력에 대해 설명합니다.

6.1.6.6.2.1. BeamDyn 성능 프로파일링 및 최적화(IPCC 1년차 및 2년차)

OpenFAST의 성능 개선을 위해 확인된 일반적인 메커니즘은 다음과 같습니다.

  • 인텔® 컴파일러 제품군 및 인텔® 수학 커널 라이브러리(인텔® MKL)

  • 알고리즘 개선

  • 보다 효율적인 캐시 사용을 가능하게 하는 메모리 액세스 최적화

  • SIMD 벡터화를 허용하는 데이터 유형 정렬

  • OpenMP를 사용한 멀티스레딩

이러한 옵션을 사용하여 앞으로 나아갈 길을 설정하기 위해 OpenFAST는 먼저 Intel® VTune™ Amplifier로 프로파일링되어 시뮬레이션에 소비된 시간을 명확하게 분석했습니다. 그런 다음 인텔® 포트란 컴파일러에서 생성된 최적화 보고서를 분석하여 자동 벡터화되지 않은 영역을 확인했습니다. 마지막으로, Intel® Advisor는 컴파일러가 멀티스레딩을 통해 잠재적으로 개선된 것으로 식별한 코드 영역을 강조하는 데 사용되었습니다.

의미 있고 현실적인 타이밍 벤치마크를 제공하기 위해 두 가지 OpenFAST 테스트 사례가 선택되었습니다. 실제 터빈 및 대기 모델 외에도 이러한 사례는 계산 비용이 많이 들고 성능 개선을 통해 차이를 만들 수 있는 영역을 드러냅니다.

5MW_Land_BD_DLL_WTurb

이 경우에 사용되는 물리 모듈은 다음과 같습니다:

  • InflowWind

  • AeroDyn 15

  • ServoDyn

이것은 BeamDyn를 구조 모듈로 사용하는 육상 기반 Jonkman 5-MW(이전의 NREL 5-MW) 터빈 시뮬레이션입니다. 0.001초의 시간 단계 크기로 20초를 시뮬레이션하고 실행됩니다. 3m 55s NLR의 이전 Peregrine 슈퍼컴퓨터(은퇴).

이 경우에 사용되는 물리 모듈은 다음과 같습니다:

6.1.6.6.2.1.1. 프로파일링

OpenFAST 테스트 사례는 성능 핫스팟을 식별하기 위해 Intel® VTune™ Amplifier로 프로파일링되었습니다. 두 가지 테스트 사례가 OpenFAST 소프트웨어의 차이점 부분을 실행하므로 서로 다른 핫스팟이 식별되었습니다. 모든 경우와 환경 설정에서 CPU 시간의 대부분은 fast_solution 루프는 각 물리 모듈의 솔루션 계산을 조정하는 고급 서브루틴입니다.

6.1.6.6.2.1.1.1. LAPACK

해외 사례에서는 LAPACK 사용량이 성능 부하로 확인됐다. 내에서 fast_solution 루프, LAPACK 함수 호출 dgetrs 전체 CPU 시간의 3.3%를 소비합니다.

6.1.6.6.2.1.1.2. BeamDyn

BeamDyn는 충실도가 높은 블레이드 응답 계산을 제공하지만 계산 비용이 많이 드는 모듈입니다. 초기 프로파일링에서는 다음을 강조했습니다. bd_elementmatrixga2 서브루틴을 핫스팟으로 사용합니다. 그러나 BeamDyn의 성능을 향상시키려는 초기 시도에서는 모듈의 데이터 구조에 대한 알고리즘 개선 및 개선의 필요성이 드러났습니다.

6.1.6.6.2.1.2. 결과

작업이 진행 중이지만 OpenFAST 솔루션 출시 시간 성능이 향상되었으며 성능 잠재력이 더 잘 이해되었습니다.

IPCC 프로젝트 첫 해의 주요 결과는 다음과 같습니다.

  • Intel® 컴파일러와 MKL 라이브러리를 사용하면 GCC 및 LAPACK보다 속도가 크게 향상됩니다.

    • 해양 시뮬레이션을 위한 MKL 스레딩을 통해 추가로 상당한 이득을 얻을 수 있습니다.

  • 해상 풍력 터빈 시뮬레이션은 모듈 전반에 걸쳐 로드 밸런싱이 제대로 이루어지지 않습니다.

    • 육상 기반 터빈 구성의 균형이 더 잘 맞습니다.

    • 더 나은 로드 밸런싱을 달성하기 위해 OpenMP 작업이 사용됩니다.

  • OpenMP 모듈 수준 병렬 처리는 다양한 모듈 작업 간의 불균형으로 인해 상당한 속도 향상을 제공하지만 제한적입니다.

  • OpenMP 및 SIMD 이점을 활성화하려면 핵심 알고리즘에 상당한 수정이 필요합니다.

NLR 하드웨어에서 최상의 성능을 발휘하도록 Intel® 도구를 조정하고 높은 수준의 멀티스레딩을 추가하면 벤치마크 사례 중 하나에서 솔루션 출시 시간이 최대 3.8배 향상되었습니다.

6.1.6.6.2.2. Linearization 루틴 프로파일링

의 일부로서 ARPA-E WEIS 프로젝트에서는 성능과 현재 병목 현상을 특성화하기 위한 노력의 일환으로 OpenFAST 내의 선형화 기능이 프로파일링되었습니다. 이 작업은 주로 FAST 라이브러리 내의 선형화 루틴을 대상으로 했습니다. FAST_Lin.f90, 개별 물리 모듈 내에서 야코비 행렬을 구성하는 루틴도 포함됩니다. 이러한 루틴을 사용하려면 대규모 행렬을 구성해야 하므로 이는 메모리 액세스 속도가 빠르고 계산 집약적인 프로세스입니다.

선형화 알고리즘의 높은 수준의 데이터 흐름 FAST_Linearize_OP 서브루틴은 아래와 같습니다.

        graph TD;
  D[Construct Module Jacobian]-->A[Calculate Module OP];
  A[Calculate Module OP]-->B[Construct Glue Code Jacobians];
  A[Calculate Module OP]-->C[Construct Glue Code State Matrices];

활성화된 각 물리 모듈은 각각의 모듈 수준 매트릭스를 구성합니다. <Module>_Jacobian 및 <Module>_GetOP 루틴, 그리고 이들의 컬렉션은 다음과 같은 전역 매트릭스로 조립됩니다. Glue_Jacobians 및 Glue_StateMatrices. 총 CPU 시간을 하향식으로 비교하면 FAST_Linearize_OP, 글루 코드 상태 행렬의 구성이 가장 비용이 많이 드는 단계임을 알 수 있습니다. HydroDyn 야코비 계산은 다른 모듈 야코비 계산과 비교해도 두드러집니다.

야코비 행렬과 상태 행렬은 입력, 출력, 연속 상태의 총 개수를 기준으로 크기가 결정됩니다. 크기는 다양하지만 이러한 행렬은 일반적으로 각 차원에 수천 개의 요소를 포함하며 대부분 0입니다. 즉, 야코비 행렬과 상태 행렬은 크고 희박합니다. 메모리 할당 및 액세스 오버헤드를 줄이려면 희소 행렬 표현이 권장됩니다.
